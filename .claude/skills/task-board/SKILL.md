# Task board

A board is a `tasks/` folder (or `<area>/tasks/`) with a `README.md` (how to take a task, generated table) and one file per task. The front matter of the task files is the single source of truth. The table is generated by the repo's `scripts/`, which also validate dependencies, cycles, duplicate ids and statuses. Without tooling the files still work by hand.

Most work needs no board. Use one when work spans several sessions, days or models, or the owner wants to track it. Do not split a feature one session can finish.

## Task file
```markdown
---
id: "006"                    # quoted; sorts with the file name
title: Short title
workstream: apps             # optional grouping
model: Sonnet 5.5            # recommended; first word is the tier (Fable|Opus|Sonnet|Haiku)
why_model: One line on why.
kind: code                   # optional: code | content | design | review
status: todo                 # todo | in-progress | review | blocked | done
claimed: 2026-11-08          # date set with in-progress
depends_on: ["003"]          # ids that must be done first
touches: [src/feature/**]    # paths this task edits, so parallel sessions avoid clashes
plan: docs/plans/006-x.md    # optional step plan, most tasks have none
---
## Prompt       self-contained: what to do, docs to read, exact names and values
## Acceptance   checkable: a command and its output, a test name, a page that loads
## Notes        risks; agents append `Ruling: <decision>. Why: <why>. Cost if wrong: <cost>.`
```

## Statuses
| Status | Meaning | Set by |
|---|---|---|
| todo | not started | the writer |
| in-progress | claimed, `claimed:` set, committed before work | the taker |
| review | built, waiting on the owner (they must try it, or it needs their secret or decision) | the worker |
| blocked | cannot continue, reason in Notes | the worker |
| done | accepted | the worker for checkable work, the owner for review items |

`review` does not unblock dependants. They stay out of the ready list until the owner sets `done`.

## Writing tasks
- **Contracts first.** Put shared schemas, interfaces and folder layout in one written plan. Parallel work is safe only when tasks meet at written contracts. A task that changes a contract edits the plan in the same commit.
- **Right size: big.** One session's work, ending in something verifiable. Fewer, larger tasks beat many small ones, since each task costs a session's start-up. Group similar work.
- **Self-contained prompt.** A worker sees only the task, CLAUDE.md, AGENTS.md and the docs it names. Give exact paths and names, never "see the chat".
- **Disjoint `touches`** for tasks meant to run in parallel. Tooling compares the fixed part of each pattern. Overlapping tasks never run together.
- **Acceptance you can check** without the author.
- Tasks that need the owner's input first start with a `grill-me` step. Decisions go in Notes as rulings.
- **Model per task**, with the tier and a one-line why:
  - Opus: contracts, design, risky or security-sensitive changes.
  - Sonnet: the default for everything else.
  - Haiku: drafting content, mechanical edits, checked by the merging session.
  - Fable: only if the owner asks.
- Cheap models take more turns on multi-step work and can cost more overall. Sonnet is the floor for work that needs judgement.

## Taking a task
1. `git pull`. Read CLAUDE.md, AGENTS.md, the board README, the task and the docs it names.
2. It must be `todo` with every `depends_on` done. Otherwise stop and say what is in the way.
3. Claim: set `status: in-progress` and `claimed: <today>`, regenerate the table, commit `Claim task NNN`. When sessions run on several machines, push the claim. A rejected push means someone else took it: pull, re-check, pick another task.
4. Work inside `touches`. Record extra paths in Notes.
5. Finish in one commit: the work, the new status, Notes and rulings, the regenerated table.
6. Reply: what changed, what was skipped or not verified, which tasks are now ready.

## Owner tracking
The repo's tooling prints counts, what is in progress (claims older than 3 days are stale), what waits on the owner, and ready tasks grouped into parallel-safe batches. Ask any session "status of the board" to run it.

## Why it is built this way
- Front matter is the source of truth and the table is generated, so the board cannot drift from the files.
- A claim is a commit. A rejected push is a free lock, and history shows who did what and when.
- Overlapping file paths were the most common failure of parallel agents, so `touches` is checked before each batch.
- Cheaper models for bulk work, decisions recorded as rulings instead of stalling, and the task file as the durable record.
